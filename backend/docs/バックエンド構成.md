# バックエンド構成の詳細設計

2026-10-01〜10-05に決めた、FastAPIへの置き換えに伴うバックエンドの詳細設計。サービス構成・パッケージの選定と
その理由は`docs/plans/user-feature-plan.md`の「バックエンド構成」、APIの仕様は`backend/docs/API設計ドラフト.md`を参照。

## 移植の方針

- 同期の仕組み(差分pull、tombstoneによる削除、削除と編集の競合の検出)は現行のまま残し、エンドポイントと処理内容を書き換える
- PostgRESTの形(`/rpc/...`・`?id=eq.`)には合わせず、`/users/{user_id}/sessions/...`のREST形式にする。
  user_idはクライアントが本文で送らず、パスパラメーターで指定してトークンと照合する
- URLにバージョン(`/v1`)は入れない。開発中の端末しか使わず、リリース版では同期を無効化するため。
  本番運用では、アプリのバージョンを見て更新を促す仕組みが別途必要になる
- 同期の管理に使う時刻(`updated_at`・`deleted_at`・差分取得の基準時刻)はサーバー時刻を正とする。
  `started_at`・`ended_at`・`recorded_at`は端末で記録した時刻(データそのもの)なので端末の時刻のまま
- `deleted_at`は「パージ予定日時」から「削除した日時」に意味を変える

## 実装方針

- 非同期(`async def`)で書く。DBアクセスはSQLAlchemy 2.xの非同期API + psycopg(v3)
  - 関連の遅延ロードは使えないので、`selectinload`等で明示的に読み込む
  - テストは`httpx.AsyncClient` + `pytest-asyncio`、Alembicは非同期用の`env.py`、workerはAPSchedulerの`AsyncIOScheduler`
- DBアクセスはORM中心で、PostGISの部分はGeoAlchemy2で書く。ストアドファンクション(`register_session_with_points`・
  `fetch_remote_sessions`)は廃止する
- レイヤ構成:

  | レイヤ | 役割 | Springで言うと |
  |---|---|---|
  | `routers` | URLとメソッドの対応、リクエストの受け取り、ステータスコード。認証は依存注入で付ける | `@RestController` |
  | `schemas` | リクエスト/レスポンスの型と入力チェック(Pydantic) | DTO + Bean Validation |
  | `services` | 業務ルール(競合の判定、所有者の確認など)とトランザクションの範囲 | `@Service` |
  | `models` | テーブルの定義(ORM) | `@Entity` |

  DB操作が増えてきたら`services`と`models`の間に`repositories`を挟む
- エラーレスポンスは`{"code": ..., "message": ..., "details": [...]}`に揃える(FastAPI既定のエラーも例外ハンドラーで変換する。
  詳細はAPI設計書の「共通事項」)
  - services層などで処理を続けられない場合は`AppError(ステータス, ErrorCode.xxx, メッセージ)`を投げる(`app/errors.py`)。
    例外ハンドラー(`app/error_handlers.py`のinstall_error_handling)がJSONレスポンスに変換する
  - bodyを受け取るエンドポイント(POST・PATCH)には`dependencies=[Depends(require_json_content_type)]`を付けて、
    Content-Typeが`application/json`でなければ415にする(`app/dependencies.py`)
  - bodyのサイズの上限(既定10MB、`MAX_REQUEST_BODY_BYTES`で変更可)はミドルウェアで全てのリクエストに適用する

## スキーマとマイグレーション

- スキーマはAlembicで管理する(`backend/alembic.ini`・`backend/migrations/`)。初期マイグレーション
  (`migrations/versions/0001_initial_schema.py`)は旧`initdb.sql`のスキーマ(users / sessions / track_points、
  インデックス、PostgRESTが使っていたストアドファンクション)をそのまま写し、変更は2本目以降のマイグレーションで行う
  - ORMのモデル(`app/models/`)はマイグレーションと同じ定義にし、`alembic check`で差分が無いことを確認する
  - マイグレーションのrevisionは連番(`0001`, `0002`, ...)を手で付け、ファイル名は`連番_内容.py`にする
- DBの中身は2段階で作る:
  1. DBコンテナの初回起動時(ボリュームが空のときだけ): `db/init/20_roles_and_databases.sh`がロール・テスト用データベース・
     拡張機能(postgis / uuid-ossp)・権限を用意する。拡張機能の作成にはスーパーユーザーの権限が必要なので、Alembicではなくここで作る。
     postgis/postgisイメージの`10_postgis.sh`の後に実行されるよう、ファイル単位でマウントしている。
     `10_postgis.sh`が開発用のデータベースに入れる使わない拡張機能(`postgis_topology`・`fuzzystrmatch`・
     `postgis_tiger_geocoder`)は削除し、`search_path`も元に戻す(`postgis_topology`が追加する`topology`スキーマの
     テーブルを`alembic check`がモデルに無いテーブルとして検出するため。テスト用のデータベースと環境を揃えるためでもある)
  2. 起動後: 開発用・テスト用の各データベースに`alembic upgrade head`を実行し、テーブル等を作る
- データベースは同じDBコンテナ(PostgreSQLサーバー)の中に2つ置く:
  - `location_db`(`POSTGRES_DB`): 開発用。api・worker(frontendの同期)が使う
  - `location_db_test`(`POSTGRES_TEST_DB`): pytest専用。`tests/conftest.py`で接続先をこちらに切り替える
- 最初のスキーマ変更(`0002_altitude_columns_to_double_precision.py`): `elevation_gain`・`max_altitude`・`min_altitude`を
  `REAL`から`double precision`にした(POSTの再送判定で値を比較するため。同期で取得したデータの精度を落とさないため)。
  PostgRESTが使っていた`register_session_with_points`も3列の値を`::real`に変換していたので、`::double precision`に作り直した
- PostgRESTの削除(`0003_remove_postgrest.py`、frontendの同期を新しいAPIへ切り替えた後): ストアドファンクションを削除し、
  `deleted_at`の意味を「削除した日時」に統一した。PostgREST時代のtombstoneは`deleted_at`にパージ予定日時(削除の90日後。
  未来の日時)が入っているので、その行だけを90日前に戻すデータ移行を行う(新しいAPIで削除した行は過去の日時なので当たらない)。
  PostgREST用のロール`web_anon`の権限も外す(ロール自体の削除はスーパーユーザーの権限が必要なので行わない。
  既存のボリュームには`web_anon`・`authenticator`が残るが、権限は無い。ボリュームを作り直せば作られない)。
  downgradeはストアドファンクションを0001・0002のファイルから読み込んで作り直す
- `postgis/postgis`イメージに含まれるPostGISのテーブル(`spatial_ref_sys`等)は、Alembicの自動生成の対象から外す
- マイグレーションは`api`の起動時には実行せず、別のコマンドで個別に実行する
  (例: `docker compose run --rm api alembic upgrade head`)。本番ではデプロイの手順の中で1回だけ実行するのが一般的なため
- 既存の開発データは移行しない。ボリュームを作り直し、シード(初期の管理者・パスワード付きのテストユーザー・
  テスト用のセッション)で入れ直す

## DBのロールと接続

- ロールを分ける(アプリに穴があってもテーブルの削除・変更はできないようにするため):

  | ロール | 用途 | 権限 |
  |---|---|---|
  | `POSTGRES_USER`(例: `postgres`) | 管理用のスーパーユーザー | 全て。拡張機能とロールの作成にだけ使う |
  | `osampo_migrator`(`MIGRATOR_DB_USER`) | マイグレーション(Alembic) | publicスキーマへのテーブルの作成・変更。テーブルの所有者になる |
  | `osampo_app`(`APP_DB_USER`) | `api` | データの読み書きのみ(DDL不可)。`sessions`・`track_points`はRLSで本人(管理者は全て)の行だけ |
  | `osampo_worker`(`WORKER_DB_USER`) | `worker` | ジョブで使うテーブル・操作だけ(下記「行レベルセキュリティ(RLS)」の「workerのロール」) |

- アプリ用のロールへの権限は、初回起動時のスクリプトで`ALTER DEFAULT PRIVILEGES FOR ROLE osampo_migrator`を
  設定し、マイグレーション用のロールが作ったテーブル・シーケンスに自動で付くようにしている
  (マイグレーションごとにGRANTを書かなくてよい)
- composeでは各サービスに必要な接続情報だけを渡す。マイグレーション用のロールは`api`(`docker compose run --rm api alembic ...`
  で使う)にだけ渡し、`worker`には渡さない
- `api`・`worker`からはcomposeのネットワーク内でサービス名`db`で接続する
- 開発中はホストのDBクライアントから確認できるよう、現行通り5432番を公開する(本番ではDockerでDBを動かさない想定)

## 設定と秘密情報

- 設定はpydantic-settingsで環境変数(`backend/.env`)から読み込む。`.env`はコミットしない
- 現行の`docker-compose.yml`に直書きされているDBパスワード(`hoge`)はやめる
- `backend/.env`はcomposeの変数展開(`${POSTGRES_PASSWORD}`等)に使い、composeから各サービスに必要な項目だけを
  環境変数として渡す。現時点の項目(`app/config.py`の`Settings`と対応):

  ```
  # 管理用のスーパーユーザー
  POSTGRES_USER=postgres
  POSTGRES_PASSWORD=<任意の文字列>
  # 開発用・テスト用のデータベース
  POSTGRES_DB=location_db
  POSTGRES_TEST_DB=location_db_test
  # マイグレーション用のロール
  MIGRATOR_DB_USER=osampo_migrator
  MIGRATOR_DB_PASSWORD=<任意の文字列>
  # api・worker用のロール
  APP_DB_USER=osampo_app
  APP_DB_PASSWORD=<任意の文字列>
  # 以下は省略可(既定値)
  # PURGE_RETENTION_DAYS=90
  # PURGE_INTERVAL_HOURS=24
  # メール送信(SMTP_HOST等)も全て省略可。既定はcomposeの中のMailpit(下記「メール送信の基盤」の「設定」)
  ```

  - ロール・パスワード・データベースはボリュームの初回作成時にだけ反映される。変えた場合は`docker compose down -v`で
    ボリュームを作り直す(作り直した後は`alembic upgrade head`とシードの投入が必要)
- 今後追加する項目:
  - JWTの署名鍵(ブロック2)
  - SMTPの接続先(ブロック3。開発中はMailpit。下記「メール送信の基盤」の「設定」)

## 起動とヘルスチェック

- `api`の`/health`(`SELECT 1`でDBに接続できるかを確認し、できなければ503)を、composeの`healthcheck`で使う。
  `/health`は運用のためのものなので、APIのパス(`/api/...`)の外に置く
- `api`・`worker`は`db`の`healthcheck`が通ってから起動する(`depends_on: condition: service_healthy`)
- 開発中の`api`はソースコード(`app/`・`tests/`・`migrations/`)をbind mountし、uvicornの`--reload`で変更を反映する。
  依存パッケージの仮想環境はイメージ内の`/opt/venv`に作るので、bind mountで隠れない
- 依存パッケージは`pyproject.toml`に書き、`uv.lock`で固定する(イメージのビルドは`uv sync --locked`)。
  `uv.lock`の生成・更新はコンテナ内(Claude Codeの環境)ではできないので、ホスト側で行う

## パージ(worker)

- `worker`は`api`と同じイメージ・同じコードで起動コマンドだけを変え、APSchedulerで定期実行する(`app/worker.py`)
- パージ期間90日・実行間隔1日(`PURGE_RETENTION_DAYS`・`PURGE_INTERVAL_HOURS`)。`deleted_at`(削除した日時)が
  パージ期間より古いtombstoneを物理削除する(`app/services/purge_service.py`。track_pointsはON DELETE CASCADEで一緒に消える)
  - 起動直後に1回実行し、以降は実行間隔ごとに実行する。前回の実行が終わっていなければ重ねて実行しない
  - 失敗してもworkerは止めず、ログに残して次の実行で再び試みる
- パージ期間はGETの`request_existence_check`の判定と同じ設定値を参照する
- 同じパージのジョブで、期限切れのリフレッシュトークン・無効にした端末のログイン状態(「認証」)と、保持期間を過ぎたメールの送信の記録
  (「メール送信の基盤」)・監査ログ(「監査ログ」)も消す
- `worker`は1つだけ起動する(複数起動するとジョブが重複して実行されるため)。メールの送信もworkerの別のジョブ(5秒ごと)で行う
- 以前は`cron`コンテナがPostgREST経由でパージしていたが、frontendの切り替えに合わせて削除した(0003)

## テスト

- pytestで書き、ホスト側で`backend/scripts/run_checks.sh`経由で実行する(中では`docker compose run --rm -T api pytest`)
- テスト用のDBは、同じPostgreSQLコンテナ内に別のデータベースとして作る(コンテナを増やさず、開発用のデータとも分けるため)。
  スキーマはAlembicで作る
- テストごとにトランザクションを開始し、終わったらロールバックして後片付けする(TRUNCATEより速いため)。
  非同期のSQLAlchemyでは、FastAPIの`dependency_overrides`でDBセッションをテスト用のものに差し替える
- 実行用のスクリプトは`backend/scripts/run_checks.sh`。frontendの`run_checks.sh`と同じ形(run_id・step・
  `SUMMARY.md`)で、結果をファイル(`backend/host_check_logs/`)に残す。stepと使い分けはCLAUDE.mdの「テスト」を参照
- lintはruffの既定のルール(`ruff check`)のみ。フォーマッタ(`ruff format`)はまだ適用していないので、チェックに含めない

## 同期APIの実装

- `app/routers/sessions.py`(HTTPの受け口)・`app/services/session_service.py`(業務ルール)・`app/schemas/session.py`
  (入力チェック)に分けている。仕様はAPI設計書
- ユーザーの確認は依存関係`verify_user_access`(`app/dependencies.py`)で行う。認証(ブロック2)を実装するまでは
  トークンを検証せず、user_idのユーザーが存在するかだけを確認する
- 時刻はDBの`clock_timestamp()`(実行した瞬間のサーバー時刻)を正とする。`now()`はトランザクションの開始時刻で固定されるため
  使わない。DBとの接続のタイムゾーンはUTCに固定し(`app/db.py`の`DB_CONNECT_ARGS`)、レスポンスの日時は常にUTC
- 既知の制約: GETの`synced_at`より前の時刻を`updated_at`に持つ書き込みが、GETの後にコミットされると、次回の差分取得で
  取りこぼしうる(書き込みのトランザクションがGETをまたいで長く続いた場合)。同一ユーザーの同時操作は想定しないので許容している
- 位置情報の型: `track_points.location`は`geography(POINTZ, 4326)`(地球上の経度・緯度・高度。距離・範囲の計算は
  メートルで行われる)。geometry型は計算には使わず、次の2か所で一時的に経由するだけ(どちらも座標の値は変わらない):
  - 登録時: `ST_MakePoint`(geometry型を返す)で点を作り、`ST_SetSRID(..., 4326)`の後にgeographyへ変換する
    (新しいAPIでは列への代入時の暗黙の変換に任せている)
  - 取得時: `ST_X`/`ST_Y`/`ST_Z`はgeometry型の関数なので、geographyからgeometryに変換してから座標を取り出す。
    SQLAlchemyで型を指定せずに`cast(..., Geometry)`すると`geometry(GEOMETRY,-1)`(2次元)への変換になり、高度を持つ点が
    エラーになるので、`Geometry(geometry_type="POINTZ", srid=4326)`を指定する
- トラックポイントの高度(altitude)はnullを許さず、nullなら422にする(2026-10-06決定)。`location`は高度込みの点(POINTZ)で
  NOT NULLのため。frontendでも高度がnullになることは無い(Geolocatorの高度はnull不可で、信頼度の低い高度は前回の点との差が
  0.5m未満・75m超のときに前回の高度で補っている)。高度を別の列に分ける案・NaNで保存する案は、実際には起きないケースのための
  仕組みになるので採らなかった
- テスト: `tests/conftest.py`の`db_session`がテストごとにトランザクションを開始し、最後にロールバックする。`api_client`は
  FastAPIの`dependency_overrides`でAPIのDBセッションを`db_session`に差し替える。APIの中の`commit()`はセーブポイントの確定になる

## 認証(ブロック2で実装。2026-10-07〜08に設計)

仕様(endpoint・code)はAPI設計書の「認証と権限」「認証のendpoints」。決定の経緯は`docs/plans/user-feature-plan.md`の「決定事項」。

- 自前で実装する。サインアップは自由登録(メールアドレスの確認コードはブロック3)。最初の管理者とテストユーザーはシードで入れる
- パスワード: 8〜128文字、文字の種類は強制しない、MFAなし。ハッシュはpwdlibのargon2(既定の設定)
- アクセストークン: ES256(公開鍵/秘密鍵)で署名したJWT、15分。中身は`sub`・`sid`・`type`・`iat`・`exp`。
  ES256にしたのは、将来のリリースや別のサービスでの検証を考えて最初から公開鍵方式にするため(サーバーが1つの間は利点は小さい)
- リフレッシュトークン: `secrets.token_urlsafe(32)`(256ビット)の文字列。DBにはSHA-256のハッシュだけを保存する
  (十分にランダムなので、argon2のような遅いハッシュは不要)。30日、使うたびに取り替える(ローテーション)。
  使用済みのものが使われたら、その端末のログイン状態を無効にする(アカウントはロックしない。圏外での再試行でも起きるため)
- 端末ごとのログイン状態とトークンの系列をセットで持つ(将来の端末の識別に備える)。アクセストークンも毎回`sid`をDBで突き合わせる
  (JWTの「DBを見ずに検証できる」利点は使わず、ログアウト・削除・停止をすぐ反映することを優先した)
- 鍵・DBパスワードのローテーションは行わない(個人開発の規模のため)

### テーブル(マイグレーション0004)

| テーブル | 主な列 | 備考 |
|---|---|---|
| `users`(拡張) | `password_hash`、`display_name`、`role`(`user`/`admin`)、`email_verified_at`、`disabled_at`、`updated_at` | `email`は小文字で保存し一意。`disabled_at`は停止(管理者が止める)で、削除のtombstoneではない。削除は物理削除 |
| `auth_sessions` | 下記 | 端末ごとのログイン状態(1回のログインに1行)。`users`の削除でCASCADE |
| `refresh_tokens` | 下記 | リフレッシュトークン(更新のたびに1行)。`auth_sessions`の削除でCASCADE |

`auth_sessions`(端末ごとのログイン状態):

| 列 | 型 | 制約 | 内容 |
|---|---|---|---|
| `id` | UUID | 主キー | アクセストークンの`sid` |
| `user_id` | UUID | NOT NULL、FK(`users.id`、ON DELETE CASCADE) | |
| `device_id` | UUID | NOT NULL | 端末が初回起動時に作ったUUID |
| `device_name` | VARCHAR(100) | null可 | 端末の表示名。今のfrontendは送らない(端末の一覧の画面を作るときに`device_info_plus`で送る) |
| `created_at` | timestamptz | NOT NULL | ログインした日時 |
| `last_used_at` | timestamptz | NOT NULL | 最後にトークンを更新した日時。毎リクエストの書き込みを避けるため、トークンの更新時だけ書き換える |
| `revoked_at` | timestamptz | null可 | 無効にした日時(ログアウト・同じ端末での再ログイン・使用済みのトークンの再使用・アカウントの停止) |

- インデックス: `user_id`(停止時にまとめて無効にするため)、`(user_id, device_id)`の部分一意インデックス(`revoked_at IS NULL`の行のみ。
  同じユーザー・同じ端末の有効なログイン状態が1つしか無いことをDBで保証する)、`revoked_at`の部分インデックス(パージ用)

`refresh_tokens`(リフレッシュトークン):

| 列 | 型 | 制約 | 内容 |
|---|---|---|---|
| `id` | UUID | 主キー | |
| `auth_session_id` | UUID | NOT NULL、FK(`auth_sessions.id`、ON DELETE CASCADE) | どの端末のログイン状態(トークンの系列)に属するか |
| `token_hash` | CHAR(64) | NOT NULL、一意 | トークンのSHA-256(16進数)。トークンそのものは保存しない |
| `expires_at` | timestamptz | NOT NULL | 発行から30日後 |
| `used_at` | timestamptz | null可 | 更新に使った日時。nullなら未使用(今使っているトークン) |
| `created_at` | timestamptz | NOT NULL | 発行した日時 |

- インデックス: `token_hash`(一意制約。更新時の検索)、`auth_session_id`、`expires_at`(パージ用)
- 1つのログイン状態の中で未使用のトークンは常に1つ。更新は1つのトランザクションで、古いトークンの行を行ロック
  (`SELECT ... FOR UPDATE`)してから`used_at`を入れ、新しいトークンを作る(同時に届いた更新は、後の方が使用済みと判定される)
- 使用済みの行は、再使用の検知のために残す。端末側はsecure storageに最新の1つだけを持つ

その他:
- 既存の`users`の行(テストユーザー`1111...`)は、マイグレーションでは`password_hash`をnullのままにし(ログインできない)、
  シードでパスワードを設定する
- `worker`のパージに追加する: 期限切れ(`expires_at`が過ぎた)のリフレッシュトークンと、無効にしてから30日経った
  ログイン状態(その端末のトークンもCASCADEで消える)を物理削除する
- `auth_sessions`を作らず`refresh_tokens`に系列のIDを持たせる案は、毎回の突き合わせが重くなり、無効にする対象が1行にならないので採らなかった
- アカウントの停止: 管理者が`disabled_at`を入れ、その人の`auth_sessions`を全て無効にする(停止を解除しても前のトークンは使えず、
  ログインし直す)。管理者の画面・APIができるまでは、管理用のコマンド(`python -m app.cli disable-user <email>`・
  `enable-user <email>`)で行う

### 鍵・設定

- ES256の鍵のペア(PEM)は`backend/secrets/`(`.gitignore`済みにする)に置き、`api`にだけ読み取り専用でマウントする。
  生成のコマンドはCLAUDE.mdの「よく使うコマンド」に書く
- 設定: `JWT_PRIVATE_KEY_PATH`・`JWT_PUBLIC_KEY_PATH`、`ACCESS_TOKEN_TTL_MINUTES`(既定15)、`REFRESH_TOKEN_TTL_DAYS`(既定30)
- 追加するパッケージ: `pwdlib[argon2]`、`PyJWT[crypto]`(ES256にcryptographyが必要)

### シード

  作れないので、管理用のコマンド(`python -m app.cli seed-dev`)で作る。開発用のパスワードは設計メモではなくシードのコード内に置く

## メール送信の基盤(ブロック3の3-1。2026-10-13に設計)

運用上の論点と、このアプリで試す範囲(Mailpitまで)の決定は`backend/docs/メール送信の運用.md`。ここでは送信基盤
(outbox + `worker`)の設計を書く。確認コード(3-2)はこの上に載せる。「Tips(外部のサーバーで送る場合)」は、今のスコープ
(Mailpit)では実装しないが、送信サービスを使うときに気にすべき観点。

### 流れ

```
api(業務の処理と同じトランザクションで outbox_emails に1行積む) ─→ commit
worker(5秒ごと) ─→ 送る時刻が来た行を1行ずつロックして取り出す ─→ smtplibでMailpitへ送る ─→ 結果を書いてcommit
```

- apiはoutboxに積むだけで、SMTPには接続しない(SMTPの接続情報もapiには渡さない)。SMTPが止まっていてもapiの応答は遅れない
- outboxは「少なくとも1回は送る(at-least-once)」。SMTPが受け取った後、結果をDBに書く前にworkerが落ちると、次の起動で同じメールを
  もう一度送る。二重に届いて困るメールを作るときは、その種類ごとに対策を考える(確認コードは2通届いても害が小さいので許容する)

### テーブル`outbox_emails`(マイグレーション0005)

| 列 | 型 | 制約 | 内容 |
|---|---|---|---|
| `id` | UUID | 主キー | |
| `recipient_user_id` | UUID | null可、FK(`users.id`、ON DELETE CASCADE) | **宛先**のユーザー(差出人はアプリ共通の`MAIL_FROM`なので行ごとには持たない。操作した人も持たない)。アカウントの削除で送信待ち・送信の記録も消す(関連データの物理削除の方針に合わせる)。ユーザーに紐づかないメールのためにnullを許す |
| `to_address` | VARCHAR(255) | NOT NULL | 宛先のメールアドレス(積んだ時点のもの)。`users.email`から引かずに持つ(下記) |
| `subject` | VARCHAR(200) | NOT NULL | 件名 |
| `body` | TEXT | null可 | 本文(テキストのみ)。**送信に成功したらnullにする**(確認コードが平文で入るため) |
| `attempts` | INTEGER | NOT NULL、既定0 | 送信を試みた回数 |
| `next_attempt_at` | timestamptz | NOT NULL | 次に送信を試みる日時。積んだ時点では積んだ日時 |
| `status` | VARCHAR(20) | NOT NULL、CHECK | `pending`(送信待ち)・`sent`(送信済み)・`failed`(諦めた)・`cancelled`(送る必要が無くなった。3-2で追加) |
| `completed_at` | timestamptz | null可 | 送信済みになった日時(SMTPサーバーが受け取った日時。相手に届いた日時ではない)、または諦めた・取り消した日時。`pending`ならnull |
| `send_deadline` | timestamptz | null可 | この日時を過ぎたら送らない(3-2で追加。マイグレーション0006)。確認コードのメールではコードの有効期限。nullなら期限なし |
| `created_at` | timestamptz | NOT NULL | 積んだ日時 |

- 状態は`status`の1列で表す(「どちらか一方しか入らない2つの日時」にしない)
- `to_address`を持つ理由: メールアドレスの変更(11月以降)では、まだ`users.email`になっていない新しいアドレスや、変更前のアドレス
  (変更の通知)に送る。積んでから送るまでの間にアドレスが変わった場合も、積んだ時点の宛先に送る。また、ユーザーの識別は`id`で、
  メールアドレスは変更・アカウントの削除で空き、別の人が登録しうるので、送った記録には送った時点のアドレスを残す
- 失敗の理由はDBに持たず、workerのログに行のidと一緒に出す(理由を調べるのはログの役割とし、DBには「いつ・誰に・何を・どうなったか」だけを残す)
- インデックス: 送信待ちの検索用に`next_attempt_at`の部分インデックス(`status = 'pending'`の行のみ)、
  `recipient_user_id`(アカウントの削除のCASCADE用)、パージ用に`created_at`
- 送信済みの行は、本文を消して「いつ誰に何の件名で送ったか」の記録として残す(「メールが届かない」という問い合わせの調査用)

### worker の送信ジョブ

- APSchedulerで5秒ごとに実行する(`MAIL_POLL_INTERVAL_SECONDS`、既定5)。前回の実行が終わっていなければ重ねて実行しない
- 1回の実行で、次を送信待ちが無くなるまで(最大20通まで)繰り返す:
  1. 送信待ちで`next_attempt_at`が過ぎた行を、`next_attempt_at`の古い順に1行、`SELECT ... FOR UPDATE SKIP LOCKED`で取り出す
     (workerは1つだけ起動する前提だが、複数になってもロックされた行を飛ばすので同じ行を同時に送らない)
  2. smtplibで送る(smtplibは同期のライブラリなので、`asyncio.to_thread`で別スレッドで動かし、イベントループを止めない)
  3. 結果(`status`・`attempts`・`next_attempt_at`・`completed_at`、成功なら本文をnullに)を書いてcommitする
     (1通ずつcommitするので、途中で落ちても送った分の結果は残る)
- 送るメールのヘッダー: `From`(`MAIL_FROM`)、`To`、`Subject`、`Date`、`Message-ID`(送信のたびに作る)。本文はUTF-8のテキストのみ

### 失敗の扱い

- 失敗を2種類に分ける(`app/mail.py`の`classify_smtp_error`):
  - **恒久的な失敗**: SMTPサーバーが宛先・本文を5xxで拒否した(宛先が存在しない等)。何度送っても結果が変わらないので、再送せずすぐに諦める
  - **一時的な失敗**: 4xxの応答、接続できない、タイムアウトなど。間隔をあけて再送する。想定外の例外も再送の対象にしてログで気づけるようにする
  - 認証の失敗・差出人の拒否も5xxだが、一時的な失敗として扱う(実装時に追加。2026-10-14)。メールごとの問題ではなく設定の誤りで
    全てのメールに共通するため、1通ずつすぐに諦めると、設定を直すまでに積まれたメールが全て失われる。再送の間にログで気づいて直す
- 再送の間隔は倍にしていく(指数バックオフ): 1回目の失敗から1分、2分、4分、8分。試行は合計5回まで(`MAIL_MAX_ATTEMPTS`、既定5)で、
  5回目も失敗したら諦める(`status`を`failed`にする)。同じ回数で長い障害(約15分)をカバーでき、復旧直後のサーバーに再送が集中しにくい
- 失敗の理由(SMTPの応答・例外)と、再送するか諦めたかはworkerのログに出す(宛先のアドレスはログに出さず、行のidで追う)
- `send_deadline`を過ぎた送信待ちの行は、送らずに`failed`にしてログに出す(3-2で追加。SMTPの不調で送信が遅れ、届いた時点で
  確認コードが期限切れになっているメールを送らないため)。送信待ちの行を取り出した時点で判定する
- Tips(外部のサーバーで送る場合):
  - 送信サービスは送信速度の上限を超えると一時的な失敗(SESなら「Throttling」)を返す。再送の間隔にランダムなずれ(ジッター)を足すと、
    多数のメールの再送が同じ瞬間に重なるのを避けられる
  - SMTPサーバーが受け取った後に相手のサーバーで届かなかった場合(バウンス)は、送信の応答ではなく後から非同期に通知される。
    これを受け取るには、送信サービスからの通知(SESならSNS等)を受ける仕組みが別に要る(Mailpitでは起きない)

### 保持とパージ

- `status`が`sent`・`failed`・`cancelled`の行は、`created_at`から90日経ったら物理削除する(`OUTBOX_RETENTION_DAYS`、既定90)。既存のパージのジョブ(1日ごと)に追加する
- Tips(外部のサーバーで送る場合): 送信サービスの側にも、宛先・件名・送信の結果のログが残る。個人情報の保持期間を決めるときは、
  アプリのDBだけでなく送信サービス側の保持期間も確認する

### 設定(`backend/.env`。全て省略可で、既定はcomposeの中のMailpit)

| 項目 | 既定 | 内容 |
|---|---|---|
| `SMTP_HOST`・`SMTP_PORT` | `mailpit`・`1025` | 送信先のSMTPサーバー |
| `SMTP_USERNAME`・`SMTP_PASSWORD` | なし | SMTPの認証(Mailpitは不要) |

| `MAIL_POLL_INTERVAL_SECONDS`・`MAIL_MAX_ATTEMPTS`・`OUTBOX_RETENTION_DAYS` | 5・5・90 | 上記の通り |

- SMTPの設定はcomposeで`worker`にだけ渡す。`worker`は`mailpit`の起動後に起動する(`depends_on`)
- Tips(外部のサーバーで送る場合): 送信サービスへは587番+STARTTLS(または465番)で接続し、認証情報(SMTP用のユーザー名・パスワード、
  またはAPIキー)は`.env`等の秘密情報として扱う。Fromのドメインは、送信サービスでドメイン認証(SPF・DKIM)を済ませたものにする。
  devcontainerのfirewallは外部のSMTPへの通信を許可していないので、ホスト側の`docker compose`から送る

## メールアドレスの確認コード(ブロック3の3-2。2026-10-14に設計)

メール送信の基盤(上記)の上に載せる。決定の経緯の要点はこの節に書き、運用上の論点は`backend/docs/メール送信の運用.md`。
APIの仕様はAPI設計書の「メールアドレスの確認」。

### 方針

- 確認はリンクではなく6桁のコードの入力。コードはサインアップ時に自動で送り、届かなければ利用者が再送する
- コードはargon2のハッシュで保存する(パスワードと同じ`pwdlib`)。6桁は100万通りしか無いので、DBが漏れればどのハッシュでも
  総当たりで割り出せる。守りの本体は10分の有効期限と入力の失敗の上限で、漏れても使える時間が短いことで許容する
  (2026-10-14決定。サーバーだけが持つ鍵を混ぜるHMACにすればDBの漏洩だけでは割り出せないが、鍵の管理が増えるので採らない)
- 制限は3つ。失敗の回数・送信の回数はリクエストをまたいで数えるので、メモリや端末ではなくDBに持つ
  (端末で数えても、攻撃者はアプリを使わずAPIを直接呼べる)

  | 制限 | 既定 | 防ぎたいこと |
  |---|---|---|
  | 1つのコードで間違えてよい回数 | 5回(再送で0に戻る) | 1つのコードの総当たり |
  | 再送の間隔 | 60秒 | 連打による大量送信 |
  | 24時間あたりの送信回数 | 5回(サインアップ時の送信を含む) | 再送の繰り返しによる総当たり・大量送信 |

  「24時間に5回」が無いと、60秒の間隔だけで1日1,440通送れ、総当たりで1日約7,200回試せ(6桁なら約0.7%)、他人のアドレスに
  大量に送りつけることもできる(2026-10-14に残すと決定)。メールアドレスは一意なので、確認コードについてはユーザー単位の上限が
  実質的にアドレス単位の上限になる
- 既知の抜け道: アカウントを削除して同じアドレスで作り直すと、制限が数え直しになる。また、多数の他人のアドレスで次々に
  サインアップされると、宛先ごとの上限では全体の量を抑えられない(対策は`tasks`ブランチの`task_candidates.md`。将来)

### テーブル`email_codes`(マイグレーション0006)

ユーザーと用途ごとに1行を持ち、送るたびに上書きする(再送のたびに行を足さない。参照先が1つに決まり、同時に届いたリクエストも
その1行のロックで順番に処理できる)。

| 列 | 型 | 制約 | 内容 |
|---|---|---|---|
| `user_id` | UUID | 主キー、FK(`users.id`、ON DELETE CASCADE) | |
| `purpose` | VARCHAR(30) | 主キー、CHECK | 用途。今は`verify_email`のみ(パスワードリセット・メールアドレスの変更を作るときに足す) |
| `code_hash` | VARCHAR(255) | null可 | 今のコードのargon2のハッシュ。確認に成功した・失敗の上限に達したらnull |
| `expires_at` | timestamptz | null可 | 今のコードの有効期限(送った10分後)。`code_hash`と同じくnullにする |
| `status` | VARCHAR(20) | NOT NULL、CHECK | `pending`(入力待ち)・`used`(確認に成功)・`locked`(失敗の上限に達した)。**期限切れは状態として保存せず`expires_at`から求める**(時間が経つだけで起き、その瞬間に処理が走らないため) |
| `failed_attempts` | INTEGER | NOT NULL | 今のコードで間違えた回数。送るたびに0に戻す |
| `issued_at` | timestamptz | NOT NULL | 最後に送った日時(再送の間隔の判定) |
| `send_count` | INTEGER | NOT NULL | 数え始めからの送信回数(24時間あたりの上限の判定) |
| `send_window_started_at` | timestamptz | NOT NULL | 送信回数の数え始め。24時間経った後の最初の送信で数え直す |
| `outbox_email_id` | UUID | null可、FK(`outbox_emails.id`、ON DELETE SET NULL) | 今のコードを送ったoutboxの行。再送のとき、まだ送られていなければ取り消す。outboxの行がパージされたらnull |

- インデックス: `outbox_email_id`(outboxのパージでのSET NULL用)
- 同じ0006で、`outbox_emails`に`send_deadline`列と`status`の`cancelled`を足す(上記「メール送信の基盤」)
- 「どのメールを取り消すか」はoutboxにメールの種類の列を足して探す案もあったが、`email_codes`が今のメールを1つ指せば済み、
  outboxを「どう送るか」だけの汎用の形に保てるので採らなかった

### 流れ

コードの送信(サインアップ時・再送)は同じ処理`issue_code`で行う:
1. `email_codes`の行をロックして読む(無ければ作る)
2. (再送のみ)前回の送信から60秒経っていなければ429。数え始めから24時間経っていれば`send_count`を0・数え始めを今にする。
   `send_count`が5なら429(数え始めから24時間経つまでの秒数を`Retry-After`で返す)
3. 前のコードのoutboxの行がまだ`pending`なら`cancelled`にする(古いコードのメールが後から届いて、入力の失敗の枠を無駄に使うのを防ぐ)
4. 6桁のコードを作り(`secrets.randbelow`)、ハッシュ・有効期限(今+10分)・`status=pending`・`failed_attempts=0`・`issued_at=今`・
   `send_count+1`で上書きする
5. outboxに積む(`send_deadline`はコードの有効期限)。積んだ行のidを`outbox_email_id`に入れる
6. 呼び出し元がcommitする(サインアップではユーザーの作成と同じトランザクション)

確認(コードの入力):
1. 確認済みのユーザー → コードを見ずに200(下記「判断の理由」)
2. `email_codes`の行をロックして読む。行が無い・`status`が`pending`でない・`expires_at`を過ぎた → 400(`verification_code_expired`)
3. コードが違う → `failed_attempts`+1。5に達したら`status=locked`にしてコード・有効期限をnullにする。commitして400(`invalid_verification_code`)
4. コードが合う → `status=used`、コード・有効期限をnull、`users.email_verified_at`=今。commitして200

状態の移り変わり:

```
            送信(60秒・24時間に5回の範囲で)
       ┌───────────────────────────┐
       ▼                           │
  [pending] ──コード一致──> [used](終わり)
    │  │
    │  └──5回間違える──> [locked] ──送信──> [pending]
    └──10分経つ──>(期限切れ。statusはpendingのまま、expires_atで判定)──送信──> [pending]
```

### 判断の理由

- コードの送信はPOST: 新しいコードを作り、メールを送り、回数を数える(状態を変える)操作で、コードはレスポンスではなくメールで届く。
  GETは「状態を変えない・何度呼んでも同じ」約束なので、ブラウザ・プロキシ等が勝手に再送・先読み・キャッシュしうる
- 確認済みでの送信は409、確認済みでの確認は(コードに関係なく)200: 確認に成功したのにレスポンスが届かず(圏外等)端末が再送した場合、
  コードは使用済みで消えているので、照合すると失敗に見えてしまう。確認済みのアカウントに確認を呼んでも何も変わらず何も漏れない
  (呼べるのはログイン中の本人だけ)ので、成功として返す。送信は意味が無いので送らず、409で確認済みを伝える

### 文面

最小限のテキストのみ。件名「【osampo-tracker】メールアドレスの確認コード」、本文はコードと有効期限(10分)と「心当たりが無い場合は破棄してください」。
有効期限の時刻は入れない(サーバーは利用者のタイムゾーンを知らないため)。

### 設定(全て省略可)

`EMAIL_CODE_TTL_MINUTES`(10)、`EMAIL_CODE_MAX_FAILED_ATTEMPTS`(5)、`EMAIL_CODE_RESEND_INTERVAL_SECONDS`(60)、`EMAIL_CODE_DAILY_LIMIT`(5)。
apiが使う(composeでapiに渡す)

- `app/services/email_verification_service.py`: `issue_verification_code`(送信。サインアップ・再送で共通)、
  `send_verification_code`(再送のendpoint)、`confirm_verification_code`(確認)。サインアップは`auth_service.signup`から呼ぶ
- `app/routers/users.py`の`send_email_verification`・`confirm_email_verification`、`app/security.py`の確認コードの生成・ハッシュ

### 確認の方法

- pytest: サインアップでコードの行とoutboxの行が1つのトランザクションでできること、再送(60秒・24時間に5回・数え直し・
  前のメールの取り消し・409)、確認(成功で`email_verified`がtrue・同期APIが使えるようになる、違うコード、5回でlocked、期限切れ、
  確認済みでの200)、outboxの`send_deadline`を過ぎた行を送らないこと。コードはoutboxの行の本文から取り出して使う

- Tips(外部のサーバーで送る場合): 日本の携帯キャリアのアドレスは「指定したドメインからのみ受信」の設定が多く、確認コードが
  届かない問い合わせの典型になる。登録画面での受信設定の案内や、届かないときの問い合わせ先を用意する

## 監査ログ(2026-10-23に設計)

認証・アカウント・権限の出来事を「誰が・何を・いつ・どこから」の形でDBに残す。不正な利用(乗っ取り・総当たり・他人のデータへの
アクセス)に気づき、後から経緯を調べるため。ログインの試行回数の制限(ブランチ`feat/login-attempt-limit`)は、この記録から失敗を数える。

### 方針

- **監査ログとアクセスログを分ける**。監査ログには意味のある出来事だけを残し、全てのリクエストの記録はアクセスログ(下記「保留」の
  ログの設計)の役割にする。正常な流れでも頻繁に起きる失敗まで入れると、見るべき出来事が埋もれるため
- 業務の処理と同じトランザクションで記録する。エラーで終わる処理(ログインの失敗等)は、記録をcommitしてからエラーを投げる
  (投げた後はロールバックされるため)。GETは業務の処理がcommitしないので、権限の確認(`verify_user_access`)で記録したらその場でcommitする
- 送信元のIPは、ASGIのミドルウェア(`app/request_context.py`)がcontextvarに入れたものをサービスの処理から参照する(引数で渡して回らないため)。
  今はリバースプロキシが無いので、コンテナに届いた接続の送信元をそのまま使う。HTTPSの構成でプロキシを置いたら、`X-Forwarded-For`等を
  どこまで信用するかを決めて取り方を見直す
- アカウントを削除したら、そのユーザーの記録も消す(関連データを全て消す方針に合わせる)。削除の記録だけは日時と`user_id`を残す。
  ユーザーは自分の`user_id`を知らないので問い合わせには使えないが、運営側が削除を実行したことを示したり、他のログ(`user_id`が残る)と
  突き合わせたりするのに使う。メールアドレス・IP・端末IDは残さない
- 保持期間は90日(`AUDIT_EVENT_RETENTION_DAYS`)。削除の記録も含めて、workerのパージで消す

### 記録する出来事

| `event_type` | いつ | 主な項目 |
|---|---|---|
| `signup` | 新規登録 | ユーザー・メールアドレス・端末ID |
| `login_succeeded` | ログインの成功 | ユーザー・メールアドレス・端末ID |
| `login_failed` | ログインの失敗。`reason`は`invalid_credentials`(メールアドレスが無い・パスワードが違う)か`account_disabled` | 入力されたメールアドレス(存在しないアドレスも残す)・該当するユーザー・端末ID |
| `login_locked` | ログインの試行回数の上限でロック中のため、照合せずに拒否した(失敗には数えない) | 入力されたメールアドレス・該当するユーザー・端末ID |
| `logout` | ログアウト | ユーザー・端末ID |
| `refresh_token_reused` | 使用済みのリフレッシュトークンの再使用(盗まれた疑い。その端末のログイン状態を無効にする) | ユーザー・端末ID |

ログアウトした他の端末からも起きる)、メールアドレスが未確認(403 `email_not_verified`。同期のたびに起きる)、404・422等。
確認コードの間違いは、コードごとの失敗の回数(`email_codes`)で制限しているので残していない。

## ログインの試行回数の制限(2026-10-23に設計)

パスワードの総当たりへの対策。失敗は監査ログ(上記)から数える(`app/services/attempt_limit_service.py`)。

### 方針

- **一時的なロック**にする。直近の成功より後の失敗が15分以内に10回たまったら、最後の失敗から15分ロックし、時間が経てば解ける
  (`AUTH_MAX_FAILED_ATTEMPTS`・`AUTH_FAILURE_WINDOW_MINUTES`・`AUTH_LOCK_MINUTES`)。管理者が解除するまでの完全なロックにすると、
  攻撃者がわざと間違え続けて本人を締め出せるため。NIST SP 800-63Bも、連続の失敗の回数を制限すること(100回以下)を求めている
- ロック中は照合せずに429(`too_many_requests`)と`Retry-After`を返し、監査ログに`login_locked`・`password_change_locked`を残す。
  ロック中の拒否は失敗に数えない(数えると、攻撃が続く限りロックが解けないため)。ロックが解けた後は、また10回試せる
- **ログインと、現在のパスワードによる再確認は別に数える**。攻撃者が違うため(ログインはログインしていない人の推測、再確認は
  ログイン状態を持つ人(盗んだトークン等)の推測)。合算すると、盗んだトークンでの間違いで本人がログインできなくなり、ログインの推測を
  続けられると本人がパスワードを変えられなくなる。ロックはそれぞれの操作にだけ効く

| | ログイン | 再確認 |
|---|---|---|
| 対象の操作 | `POST /api/auth/login` | `PUT /api/users/me/password`(メールアドレスの変更を作ったら加える) |
| 数える単位 | 入力されたメールアドレス(小文字にそろえる)。存在しないアドレスも同じように数える(ロックの有無で登録の有無が分からないように) | ユーザー |
| 失敗 | `login_failed`のうち`reason`が`invalid_credentials`のもの(停止中のアカウントでの失敗はパスワードが合っていたので数えない) | `password_change_failed` |
| 数え直す成功 | `login_succeeded` | `password_changed` |

- 送信元のIP単位の制限は入れていない(IPは監査ログに記録だけする)。多くのアカウントを少しずつ試す攻撃には効かないが、IPで数えるには
  HTTPSの構成でリバースプロキシを置いたときに`X-Forwarded-For`をどこまで信用するかを決める必要があり、モバイル回線では多くの端末が
  同じIPを共有するため、HTTPSの構成と一緒に検討する
- 同時に届いたリクエストで判定と失敗の記録の間に割り込まれないよう、判定の前にメールアドレス(再確認はユーザー)ごとのadvisory lock
  (`pg_advisory_xact_lock`)を取り、記録をcommitするまで持つ。同じメールアドレスのログインは1件ずつ処理されることになる

### 判定

直近の成功より後の失敗を新しい順に最大10件取り、10件あって、最も新しいものと最も古いものの差が15分未満ならロック中とし、
「最も新しい失敗+15分」まで拒否する。インデックスは監査ログの`(email, occurred_at)`・`(user_id, occurred_at)`を使う。

### テスト

`tests/test_attempt_limit.py`: APIで10回間違えた後のロック(ログイン・パスワードの変更)、存在しないメールアドレス、メールアドレスごと・
ユーザーごと、ロックの期限切れ、ウィンドウの外の失敗、成功での数え直し、停止中のアカウントでの失敗、ログインと再確認が別であること。

## ログ(2026-10-23に設計)

### 3つのログの役割

| | アクセスログ | アプリのログ | 監査ログ(上記) |
|---|---|---|---|
| 説明すること | どんなリクエストが来て、どう応えたか | システムが中で何をしたか、なぜその結果になったか | 誰が、どのアカウントに何をしたか |
| 単位 | 全てのリクエストを1行ずつ(同じ形) | 判断の分かれ目・異常・重要な節目があったときだけ(普通のリクエストでは出ない) | 人の操作のうち、セキュリティ上あとから説明が要るもの |
| 出力先 | 標準出力(ロガー`app.access`) | 標準出力(モジュールごとのロガー) | DB(`audit_events`) |

- アクセスログには、全てのリクエストを同じ形の1行で残すことに意味があるので、リクエストごとの詳細は入れない。詳細(理由・件数・ID・
  スタックトレース)はアプリのログで補う。HTTPではない処理(workerのパージ・メール送信)や起動・設定の誤りもアプリのログの役割
- アプリのログにも監査ログと同じ制約がかかる。中身ではなくIDと件数を出す

### 出さないもの

パスワード・トークン・確認コード・メール本文・位置情報(リクエストのbody)・メールアドレス(監査ログにだけ残す)・クエリ文字列・
他ユーザーのuser_id(404・409の理由で「他ユーザーのもの」と分かっても、そのユーザーは出さない)

### 形式(`LOG_FORMAT`・`LOG_LEVEL`)

- 既定はkey=valueのテキスト(logfmt)。人が読めて`grep status=500`でも探せ、多くのログの基盤がそのまま項目として読み取れる。
  `LOG_FORMAT=json`で1行1つのJSONにできる(ログを集めて検索する基盤(CloudWatch Logs等)に載せるとき用)。ログを出す側は同じで、
  整形(`app/logging_config.py`のFormatter)だけを切り替える

```
2026-10-23T05:05:12.345Z INFO app.access request request_id=8f3c… user_id=1111… ip=172.18.0.1 method=DELETE path=/api/users/{user_id}/sessions/{session_id} status=404 code=session_not_found duration_ms=12.3
2026-10-23T05:05:12.340Z INFO app.services.session_service session not found request_id=8f3c… user_id=1111… session_id=ab12… reason=other_user
2026-10-23T05:10:00.001Z INFO app.worker purged tombstones=3 refresh_tokens=12 auth_sessions=0 outbox_emails=5 audit_events=40
```

- 外部のライブラリ(structlog等)は使わず、Python標準のloggingにFormatterを2種類足して作った(仕組みを理解するため)。
  ログを出す側は項目を`extra`で渡す。リクエストの中で出したログには、LogRecordを作るところ(`setLogRecordFactory`)で
  リクエストIDとuser_idを付ける(どのハンドラーで出しても付くように。そのため、この2つはextraで渡さない)
- レベルの目安: ERROR=人が対応すべき失敗(500の例外、メールを諦めた、パージの失敗)、WARNING=自動で回復するが続くと問題
  (SMTPに接続できず再送)、INFO=正常な重要な節目と判断の理由(起動、ジョブの結果、404・409の理由)、DEBUG=開発中の細部。既定はINFO
- uvicornのログもルートのロガーに流して同じ形式にし、uvicorn標準のアクセスログは止める(`--no-access-log`)

### リクエストID

- `app/request_context.py`のミドルウェアが、リクエストごとにID・送信元のIP・認証したユーザー・エラーのcodeをcontextvarに持ち、
  レスポンスの`X-Request-ID`ヘッダーに付け、終わったらアクセスログを1行出す
- 端末が送った`X-Request-ID`は、形式(英数字と`-`の8〜64文字)に合えば使う(任意の文字列をログに書き込ませないため、合わなければ
  サーバーで作る)。端末はリクエストごとにUUIDを作って送り、失敗したときに端末のログに出す(応答が届かなかった場合でも探せるように)
- 監査ログにも残す(`audit_events.request_id`)。アカウントの削除の記録には残さない(日時とuser_idだけ、の決定どおり)
- 想定外の例外(500)は、このミドルウェアの中でスタックトレースをログに出してから投げ直す。500のレスポンスを作るStarletteの
  `ServerErrorMiddleware`はこれより外側で動き、そこではリクエストの情報を参照できないため(リクエストIDはscopeに置いて渡す)

### アクセスログの項目

`request_id`・`user_id`(認証できたもの)・`ip`・`method`・`path`(パスの型。どのルートにも当たらなければ実際のパスを200文字まで)・
`status`・`code`(エラーのcode)・`duration_ms`

### アプリのログで出す判断の理由

| 場面 | メッセージ | 項目 |
|---|---|---|
| PATCH・DELETE・restoreの404(`session_not_found`) | `session not found` | `session_id`、`reason`(`not_exists`・`other_user`) |
| 登録の409(`id_conflicted`) | `session id conflicted` | `session_id`、`reason`(`other_user`・`different_session`) |
| 削除と編集の競合(409 `deleted`) | `session edit conflicted with deletion` | `session_id`、`action`(`edit`・`resend`) |

### 保持

- Dockerのjson-fileのログに、サービスごとに10MB×3ファイルまで(composeの`x-logging`)。それより古いものは消える
- 本番でのログの集約先・保持期間(CloudWatch Logs等)は、HTTPSの構成と一緒に決める。user_id・IPは個人関連情報として扱い、保持期間を決める

### テスト

`tests/test_logging.py`: リクエストIDの生成・端末の値の採用・不正な値の置き換え、アクセスログの項目(パスの型・ステータス・user_id・
code・どのルートにも当たらないパス)、500のログとリクエストID、404の理由、監査ログのリクエストID、テキスト・JSONの整形

## 行レベルセキュリティ(RLS)(2026-10-26に設計)

アプリ層の分離(`verify_user_access`でパスの`user_id`とトークンのユーザーを比べる)に加えて、DBでも本人の行だけを扱えるようにする
(多層防御。アプリにクエリの条件の書き忘れ等があっても他人の行に届かない)。

### 方針(決定)

- **対象は`sessions`・`track_points`だけ**。認証系(`users`・`auth_sessions`・`refresh_tokens`・`email_codes`)・`outbox_emails`・
  `audit_events`は対象外(ログインの時点ではユーザーが決まっていないため、RLSと相性が悪い)
- **ホワイトリスト(未設定なら0件)**: apiはトランザクションごとに今のユーザーのIDを`set_config('app.user_id', <ID>, true)`
  (=`SET LOCAL`)で渡し、ポリシーはそのユーザーの行だけを許す。渡し忘れたときは全件ではなく何も見えない側に倒れる
- **`track_points`**: `user_id`の列を持たず、`session_id`経由で`sessions`の`user_id`と比べる(`EXISTS`のサブクエリ)。
  INSERTの検査にも同じ条件を使い、他人のsessionにtrack_pointを足せないようにする
- **管理者**: DBのロールは分けない。apiは`app.user_id`だけを渡し、ポリシーが`users.role`を引いて管理者か判定する
  (管理者かどうかの根拠を`users.role`の1か所にし、apiの不具合で「管理者のふり」ができないようにする)。
  管理者は全ての行を読み書きできる
- **書き込みの検査(`WITH CHECK`)**: 一般ユーザーにだけかけ、自分の`user_id`(`track_points`は自分のsession)でしか書けないようにする。
  管理者・`worker`・`osampo_migrator`にはかけない
- **`worker`**: 専用のロールを作り、`api`とは別の接続情報にする。パージのために`sessions`の全行を扱えるよう、`BYPASSRLS`の属性ではなく
  そのロール向けのポリシー(`TO <workerのロール> USING (true)`)で許す(素通りできるテーブルと操作がマイグレーションに残り、権限も最小にできる)。
  `track_points`は`sessions`のON DELETE CASCADEで消える(外部キーの処理はRLSの対象外)ので、ポリシーは要らない
- **`osampo_migrator`(テーブルの所有者)**: `FORCE ROW LEVEL SECURITY`を付けず、RLSの対象外のままにする。`db/seed.sql`の投入・
  外部キーのCASCADEは今のまま動く。apiを誤ってmigratorの接続情報で起動するとRLSが黙って無効になるので、テストで
  「apiのロールがテーブルの所有者でないこと」「対象のテーブルでRLSが有効なこと」を確認する

### 今のユーザーを渡すタイミング

`SET LOCAL`はトランザクションが終わると消える。一般ユーザーが自分を指定する同期APIは、認証からserviceの最後のcommitまでが
1つのトランザクションなので1回渡せば足りる。管理者が他のユーザーを指定する場合だけ、トランザクションが2つになる:

1. `get_auth_context`(`authenticate`): トークンを検証し、`users`・`auth_sessions`を読む(1つ目のトランザクションが始まる)
2. `verify_user_access`: 対象のユーザーの存在を確認し、監査ログ(`admin_user_access`)を積んで**commit**(1つ目が終わる)
3. service: `sessions`を読み書きして**commit**(2つ目)。ここで`app.user_id`が消えていると0件になり、管理者なのに404になる

SQLAlchemyのセッションの`after_begin`イベントで、トランザクションが始まるたびに`set_config`する(2026-10-26に決定)。
認証が終わった時点でセッションに今のユーザーを記録し(`session.info`)、その時点で始まっているトランザクションにもすぐ渡す。
以降はcommitの場所が増えても渡し忘れが起きない。管理者の経路だけ渡し直す案・1つのトランザクションにまとめる案は、
commitの場所が変わると壊れる(後者はGETで監査ログをcommitする場所も変わる)ので採らなかった。

### ポリシー(案)

```sql
-- 今のユーザー(未設定ならNULL)。一度SET LOCALした接続では、トランザクションの終了後に''へ戻ることがあるのでNULLIFで受ける
NULLIF(current_setting('app.user_id', true), '')::uuid
-- 管理者か。行に依存しないサブクエリなので、1回の検索につき1回だけ実行される
EXISTS (SELECT 1 FROM users WHERE id = <今のユーザー> AND role = 'admin')
```

| テーブル | ポリシー | 対象のロール | 操作 | USING(読める・変えられる行) | WITH CHECK(書ける値) |
|---|---|---|---|---|---|
| `sessions` | 本人 | api | 全て | `user_id = <今のユーザー>` | 同左 |
| `sessions` | 管理者 | api | 全て | 管理者か | 管理者か |
| `sessions` | パージ | worker | SELECT・DELETE | `true` | - |
| `track_points` | 本人 | api | 全て | `EXISTS (sessions s WHERE s.id = session_id AND s.user_id = <今のユーザー>)` | 同左 |
| `track_points` | 管理者 | api | 全て | 管理者か | 管理者か |

- 同じテーブル・操作の複数のポリシーはOR(permissive)で組み合わさる
- 関数にまとめるか(`app_current_user_id()`等)、各ポリシーに直接書くかは実装時に決める

### 既存のコードへの影響

- **POSTの`id_conflicted`**: 他人のsessionが見えなくなるので、SELECTも`INSERT ... ON CONFLICT DO NOTHING`も0件になり、今は2回の
  ループの後に`RuntimeError`(500)になる。INSERTが衝突で0件になり、その後のSELECTでも見えなければ「他人の行との衝突」として
  409 `id_conflicted`にする(一意制約はRLSに関係なく効く。他人の行の中身を見ずに判定できる)
- **テスト**: `tests/conftest.py`はapiと同じロールで接続するので、テストにもRLSがかかる。準備のデータを直接INSERTしているテスト
  (`test_models.py`・`test_purge.py`・`test_logging.py`)は、ユーザーを設定する補助関数か、workerのロールでの接続が要る

### workerのロール(`osampo_worker`)

- 接続情報は`WORKER_DB_USER`・`WORKER_DB_PASSWORD`(`backend/.env`)。ロールはサーバー全体のものなのでmigratorでは作れず、
  `db/init`で作る。`worker`には今の`APP_DB_*`の代わりにこちらを渡す
- **権限は今のジョブで使うテーブル・操作だけにする(最小権限)**。`ALTER DEFAULT PRIVILEGES`は付けないので、workerが新しい
  テーブルを使うときは、そのマイグレーションでGRANTを足す:

  | テーブル | 権限 | 使うジョブ |
  |---|---|---|
  | `sessions` | SELECT・DELETE | tombstoneのパージ(条件で列を読むのでSELECTも要る) |
  | `refresh_tokens` | SELECT・DELETE | 期限切れのトークンのパージ |
  | `auth_sessions` | SELECT・DELETE | 無効にしたログイン状態のパージ |
  | `outbox_emails` | SELECT・UPDATE・DELETE | 送信(`FOR UPDATE`で取り出して結果を書く)・送信の記録のパージ |
  | `audit_events` | SELECT・DELETE | 監査ログのパージ |

  `track_points`(sessionsのCASCADE)・`refresh_tokens`(auth_sessionsのCASCADE)の連鎖の削除は外部キーの処理として行われるので、
  workerにそのテーブルの権限は要らない。`users`・シーケンスも使わない
