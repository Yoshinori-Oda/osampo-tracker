# バックエンド構成の詳細設計

2026-10-01〜10-05に決めた、FastAPIへの置き換えに伴うバックエンドの詳細設計。サービス構成・パッケージの選定と
その理由は`docs/plans/user-feature-plan.md`の「バックエンド構成」、APIの仕様は`backend/docs/API設計ドラフト.md`を参照。

## 移植の方針

- 同期の仕組み(差分pull、tombstoneによる削除、削除と編集の競合の検出)は現行のまま残し、エンドポイントと処理内容を書き換える
- PostgRESTの形(`/rpc/...`・`?id=eq.`)には合わせず、`/users/{user_id}/sessions/...`のREST形式にする。
  user_idはクライアントが本文で送らず、パスパラメーターで指定してトークンと照合する
- URLにバージョン(`/v1`)は入れない。開発中の端末しか使わず、リリース版では同期を無効化するため。
  本番運用では、アプリのバージョンを見て更新を促す仕組みが別途必要になる
- 同期の管理に使う時刻(`updated_at`・`deleted_at`・差分取得の基準時刻)はサーバー時刻を正とする。
  `started_at`・`ended_at`・`recorded_at`は端末で記録した時刻(データそのもの)なので端末の時刻のまま
- `deleted_at`は「パージ予定日時」から「削除した日時」に意味を変える

## 実装方針

- 非同期(`async def`)で書く。DBアクセスはSQLAlchemy 2.xの非同期API + psycopg(v3)
  - 関連の遅延ロードは使えないので、`selectinload`等で明示的に読み込む
  - テストは`httpx.AsyncClient` + `pytest-asyncio`、Alembicは非同期用の`env.py`、workerはAPSchedulerの`AsyncIOScheduler`
- DBアクセスはORM中心で、PostGISの部分はGeoAlchemy2で書く。ストアドファンクション(`register_session_with_points`・
  `fetch_remote_sessions`)は廃止する
- レイヤ構成:

  | レイヤ | 役割 | Springで言うと |
  |---|---|---|
  | `routers` | URLとメソッドの対応、リクエストの受け取り、ステータスコード。認証は依存注入で付ける | `@RestController` |
  | `schemas` | リクエスト/レスポンスの型と入力チェック(Pydantic) | DTO + Bean Validation |
  | `services` | 業務ルール(競合の判定、所有者の確認など)とトランザクションの範囲 | `@Service` |
  | `models` | テーブルの定義(ORM) | `@Entity` |

  DB操作が増えてきたら`services`と`models`の間に`repositories`を挟む
- エラーレスポンスは`{"code": ..., "message": ..., "details": [...]}`に揃える(FastAPI既定のエラーも例外ハンドラーで変換する。
  詳細はAPI設計書の「共通事項」)
  - services層などで処理を続けられない場合は`AppError(ステータス, ErrorCode.xxx, メッセージ)`を投げる(`app/errors.py`)。
    例外ハンドラー(`app/error_handlers.py`のinstall_error_handling)がJSONレスポンスに変換する
  - bodyを受け取るエンドポイント(POST・PATCH)には`dependencies=[Depends(require_json_content_type)]`を付けて、
    Content-Typeが`application/json`でなければ415にする(`app/dependencies.py`)
  - bodyのサイズの上限(既定10MB、`MAX_REQUEST_BODY_BYTES`で変更可)はミドルウェアで全てのリクエストに適用する

## スキーマとマイグレーション

- スキーマはAlembicで管理する(`backend/alembic.ini`・`backend/migrations/`)。初期マイグレーション
  (`migrations/versions/0001_initial_schema.py`)は旧`initdb.sql`のスキーマ(users / sessions / track_points、
  インデックス、PostgRESTが使っていたストアドファンクション)をそのまま写し、変更は2本目以降のマイグレーションで行う
  - ORMのモデル(`app/models/`)はマイグレーションと同じ定義にし、`alembic check`で差分が無いことを確認する
  - マイグレーションのrevisionは連番(`0001`, `0002`, ...)を手で付け、ファイル名は`連番_内容.py`にする
- DBの中身は2段階で作る:
  1. DBコンテナの初回起動時(ボリュームが空のときだけ): `db/init/20_roles_and_databases.sh`がロール・テスト用データベース・
     拡張機能(postgis / uuid-ossp)・権限を用意する。拡張機能の作成にはスーパーユーザーの権限が必要なので、Alembicではなくここで作る。
     postgis/postgisイメージの`10_postgis.sh`の後に実行されるよう、ファイル単位でマウントしている。
     `10_postgis.sh`が開発用のデータベースに入れる使わない拡張機能(`postgis_topology`・`fuzzystrmatch`・
     `postgis_tiger_geocoder`)は削除し、`search_path`も元に戻す(`postgis_topology`が追加する`topology`スキーマの
     テーブルを`alembic check`がモデルに無いテーブルとして検出するため。テスト用のデータベースと環境を揃えるためでもある)
  2. 起動後: 開発用・テスト用の各データベースに`alembic upgrade head`を実行し、テーブル等を作る
- データベースは同じDBコンテナ(PostgreSQLサーバー)の中に2つ置く:
  - `location_db`(`POSTGRES_DB`): 開発用。api・worker(frontendの同期)が使う
  - `location_db_test`(`POSTGRES_TEST_DB`): pytest専用。`tests/conftest.py`で接続先をこちらに切り替える
- 最初のスキーマ変更(`0002_altitude_columns_to_double_precision.py`): `elevation_gain`・`max_altitude`・`min_altitude`を
  `REAL`から`double precision`にした(POSTの再送判定で値を比較するため。同期で取得したデータの精度を落とさないため)。
  PostgRESTが使っていた`register_session_with_points`も3列の値を`::real`に変換していたので、`::double precision`に作り直した
- PostgRESTの削除(`0003_remove_postgrest.py`、frontendの同期を新しいAPIへ切り替えた後): ストアドファンクションを削除し、
  `deleted_at`の意味を「削除した日時」に統一した。PostgREST時代のtombstoneは`deleted_at`にパージ予定日時(削除の90日後。
  未来の日時)が入っているので、その行だけを90日前に戻すデータ移行を行う(新しいAPIで削除した行は過去の日時なので当たらない)。
  PostgREST用のロール`web_anon`の権限も外す(ロール自体の削除はスーパーユーザーの権限が必要なので行わない。
  既存のボリュームには`web_anon`・`authenticator`が残るが、権限は無い。ボリュームを作り直せば作られない)。
  downgradeはストアドファンクションを0001・0002のファイルから読み込んで作り直す
- `postgis/postgis`イメージに含まれるPostGISのテーブル(`spatial_ref_sys`等)は、Alembicの自動生成の対象から外す
- マイグレーションは`api`の起動時には実行せず、別のコマンドで個別に実行する
  (例: `docker compose run --rm api alembic upgrade head`)。本番ではデプロイの手順の中で1回だけ実行するのが一般的なため
- 既存の開発データは移行しない。ボリュームを作り直し、シード(初期の管理者・パスワード付きのテストユーザー・
  テスト用のセッション)で入れ直す

## DBのロールと接続

- ロールを分ける(アプリに穴があってもテーブルの削除・変更はできないようにするため):

  | ロール | 用途 | 権限 |
  |---|---|---|
  | `POSTGRES_USER`(例: `postgres`) | 管理用のスーパーユーザー | 全て。拡張機能とロールの作成にだけ使う |
  | `osampo_migrator`(`MIGRATOR_DB_USER`) | マイグレーション(Alembic) | publicスキーマへのテーブルの作成・変更。テーブルの所有者になる |
  | `osampo_app`(`APP_DB_USER`) | `api`・`worker` | データの読み書きのみ(DDL不可) |

- アプリ用のロールへの権限は、初回起動時のスクリプトで`ALTER DEFAULT PRIVILEGES FOR ROLE osampo_migrator`を
  設定し、マイグレーション用のロールが作ったテーブル・シーケンスに自動で付くようにしている
  (マイグレーションごとにGRANTを書かなくてよい)
- composeでは各サービスに必要な接続情報だけを渡す。マイグレーション用のロールは`api`(`docker compose run --rm api alembic ...`
  で使う)にだけ渡し、`worker`には渡さない
- `api`・`worker`からはcomposeのネットワーク内でサービス名`db`で接続する
- 開発中はホストのDBクライアントから確認できるよう、現行通り5432番を公開する(本番ではDockerでDBを動かさない想定)

## 設定と秘密情報

- 設定はpydantic-settingsで環境変数(`backend/.env`)から読み込む。`.env`はコミットしない
- 現行の`docker-compose.yml`に直書きされているDBパスワード(`hoge`)はやめる
- `backend/.env`はcomposeの変数展開(`${POSTGRES_PASSWORD}`等)に使い、composeから各サービスに必要な項目だけを
  環境変数として渡す。現時点の項目(`app/config.py`の`Settings`と対応):

  ```
  # 管理用のスーパーユーザー
  POSTGRES_USER=postgres
  POSTGRES_PASSWORD=<任意の文字列>
  # 開発用・テスト用のデータベース
  POSTGRES_DB=location_db
  POSTGRES_TEST_DB=location_db_test
  # マイグレーション用のロール
  MIGRATOR_DB_USER=osampo_migrator
  MIGRATOR_DB_PASSWORD=<任意の文字列>
  # api・worker用のロール
  APP_DB_USER=osampo_app
  APP_DB_PASSWORD=<任意の文字列>
  # 以下は省略可(既定値)
  # PURGE_RETENTION_DAYS=90
  # PURGE_INTERVAL_HOURS=24
  ```

  - ロール・パスワード・データベースはボリュームの初回作成時にだけ反映される。変えた場合は`docker compose down -v`で
    ボリュームを作り直す(作り直した後は`alembic upgrade head`とシードの投入が必要)
- 今後追加する項目:
  - JWTの署名鍵(ブロック2)
  - SMTPの接続先(ブロック3。開発中はMailpit)

## 起動とヘルスチェック

- `api`の`/health`(`SELECT 1`でDBに接続できるかを確認し、できなければ503)を、composeの`healthcheck`で使う。
  `/health`は運用のためのものなので、APIのパス(`/api/...`)の外に置く
- `api`・`worker`は`db`の`healthcheck`が通ってから起動する(`depends_on: condition: service_healthy`)
- 開発中の`api`はソースコード(`app/`・`tests/`・`migrations/`)をbind mountし、uvicornの`--reload`で変更を反映する。
  依存パッケージの仮想環境はイメージ内の`/opt/venv`に作るので、bind mountで隠れない
- 依存パッケージは`pyproject.toml`に書き、`uv.lock`で固定する(イメージのビルドは`uv sync --locked`)。
  `uv.lock`の生成・更新はコンテナ内(Claude Codeの環境)ではできないので、ホスト側で行う

## パージ(worker)

- `worker`は`api`と同じイメージ・同じコードで起動コマンドだけを変え、APSchedulerで定期実行する(`app/worker.py`)
- パージ期間90日・実行間隔1日(`PURGE_RETENTION_DAYS`・`PURGE_INTERVAL_HOURS`)。`deleted_at`(削除した日時)が
  パージ期間より古いtombstoneを物理削除する(`app/services/purge_service.py`。track_pointsはON DELETE CASCADEで一緒に消える)
  - 起動直後に1回実行し、以降は実行間隔ごとに実行する。前回の実行が終わっていなければ重ねて実行しない
  - 失敗してもworkerは止めず、ログに残して次の実行で再び試みる
- パージ期間はGETの`request_existence_check`の判定と同じ設定値を参照する
- `worker`は1つだけ起動する(複数起動するとジョブが重複して実行されるため)
- 以前は`cron`コンテナがPostgREST経由でパージしていたが、frontendの切り替えに合わせて削除した(0003)

## テスト

- pytestで書き、ホスト側で`backend/scripts/run_checks.sh`経由で実行する(中では`docker compose run --rm -T api pytest`)
- テスト用のDBは、同じPostgreSQLコンテナ内に別のデータベースとして作る(コンテナを増やさず、開発用のデータとも分けるため)。
  スキーマはAlembicで作る
- テストごとにトランザクションを開始し、終わったらロールバックして後片付けする(TRUNCATEより速いため)。
  非同期のSQLAlchemyでは、FastAPIの`dependency_overrides`でDBセッションをテスト用のものに差し替える
- 実行用のスクリプトは`backend/scripts/run_checks.sh`。frontendの`run_checks.sh`と同じ形(run_id・step・
  `SUMMARY.md`)で、結果をファイル(`backend/host_check_logs/`)に残す。stepと使い分けはCLAUDE.mdの「テスト」を参照
- lintはruffの既定のルール(`ruff check`)のみ。フォーマッタ(`ruff format`)はまだ適用していないので、チェックに含めない

## 同期APIの実装

- `app/routers/sessions.py`(HTTPの受け口)・`app/services/session_service.py`(業務ルール)・`app/schemas/session.py`
  (入力チェック)に分けている。仕様はAPI設計書
- ユーザーの確認は依存関係`verify_user_access`(`app/dependencies.py`)で行う。認証(ブロック2)を実装するまでは
  トークンを検証せず、user_idのユーザーが存在するかだけを確認する
- 時刻はDBの`clock_timestamp()`(実行した瞬間のサーバー時刻)を正とする。`now()`はトランザクションの開始時刻で固定されるため
  使わない。DBとの接続のタイムゾーンはUTCに固定し(`app/db.py`の`DB_CONNECT_ARGS`)、レスポンスの日時は常にUTC
- 既知の制約: GETの`synced_at`より前の時刻を`updated_at`に持つ書き込みが、GETの後にコミットされると、次回の差分取得で
  取りこぼしうる(書き込みのトランザクションがGETをまたいで長く続いた場合)。同一ユーザーの同時操作は想定しないので許容している
- 位置情報の型: `track_points.location`は`geography(POINTZ, 4326)`(地球上の経度・緯度・高度。距離・範囲の計算は
  メートルで行われる)。geometry型は計算には使わず、次の2か所で一時的に経由するだけ(どちらも座標の値は変わらない):
  - 登録時: `ST_MakePoint`(geometry型を返す)で点を作り、`ST_SetSRID(..., 4326)`の後にgeographyへ変換する
    (新しいAPIでは列への代入時の暗黙の変換に任せている)
  - 取得時: `ST_X`/`ST_Y`/`ST_Z`はgeometry型の関数なので、geographyからgeometryに変換してから座標を取り出す。
    SQLAlchemyで型を指定せずに`cast(..., Geometry)`すると`geometry(GEOMETRY,-1)`(2次元)への変換になり、高度を持つ点が
    エラーになるので、`Geometry(geometry_type="POINTZ", srid=4326)`を指定する
- トラックポイントの高度(altitude)はnullを許さず、nullなら422にする(2026-10-06決定)。`location`は高度込みの点(POINTZ)で
  NOT NULLのため。frontendでも高度がnullになることは無い(Geolocatorの高度はnull不可で、信頼度の低い高度は前回の点との差が
  0.5m未満・75m超のときに前回の高度で補っている)。高度を別の列に分ける案・NaNで保存する案は、実際には起きないケースのための
  仕組みになるので採らなかった
- テスト: `tests/conftest.py`の`db_session`がテストごとにトランザクションを開始し、最後にロールバックする。`api_client`は
  FastAPIの`dependency_overrides`でAPIのDBセッションを`db_session`に差し替える。APIの中の`commit()`はセーブポイントの確定になる

## 認証(ブロック2で実装。2026-10-07〜08に設計)

仕様(endpoint・code)はAPI設計書の「認証と権限」「認証のendpoints」。決定の経緯は`docs/plans/user-feature-plan.md`の「決定事項」。

- 自前で実装する。サインアップは自由登録(メールアドレスの確認コードはブロック3)。最初の管理者とテストユーザーはシードで入れる
- パスワード: 8〜128文字、文字の種類は強制しない、MFAなし。ハッシュはpwdlibのargon2(既定の設定)
- アクセストークン: ES256(公開鍵/秘密鍵)で署名したJWT、15分。中身は`sub`・`sid`・`type`・`iat`・`exp`。
  ES256にしたのは、将来のリリースや別のサービスでの検証を考えて最初から公開鍵方式にするため(サーバーが1つの間は利点は小さい)
- リフレッシュトークン: `secrets.token_urlsafe(32)`(256ビット)の文字列。DBにはSHA-256のハッシュだけを保存する
  (十分にランダムなので、argon2のような遅いハッシュは不要)。30日、使うたびに取り替える(ローテーション)。
  使用済みのものが使われたら、その端末のログイン状態を無効にする(アカウントはロックしない。圏外での再試行でも起きるため)
- 端末ごとのログイン状態とトークンの系列をセットで持つ(将来の端末の識別に備える)。アクセストークンも毎回`sid`をDBで突き合わせる
  (JWTの「DBを見ずに検証できる」利点は使わず、ログアウト・削除・停止をすぐ反映することを優先した)
- 鍵・DBパスワードのローテーションは行わない(個人開発の規模のため)

### テーブル(マイグレーション0004)

| テーブル | 主な列 | 備考 |
|---|---|---|
| `users`(拡張) | `password_hash`、`display_name`、`role`(`user`/`admin`)、`email_verified_at`、`disabled_at`、`updated_at` | `email`は小文字で保存し一意。`disabled_at`は停止(管理者が止める)で、削除のtombstoneではない。削除は物理削除 |
| `auth_sessions` | 下記 | 端末ごとのログイン状態(1回のログインに1行)。`users`の削除でCASCADE |
| `refresh_tokens` | 下記 | リフレッシュトークン(更新のたびに1行)。`auth_sessions`の削除でCASCADE |

`auth_sessions`(端末ごとのログイン状態):

| 列 | 型 | 制約 | 内容 |
|---|---|---|---|
| `id` | UUID | 主キー | アクセストークンの`sid` |
| `user_id` | UUID | NOT NULL、FK(`users.id`、ON DELETE CASCADE) | |
| `device_id` | UUID | NOT NULL | 端末が初回起動時に作ったUUID |
| `device_name` | VARCHAR(100) | null可 | 端末の表示名。今のfrontendは送らない(端末の一覧の画面を作るときに`device_info_plus`で送る) |
| `created_at` | timestamptz | NOT NULL | ログインした日時 |
| `last_used_at` | timestamptz | NOT NULL | 最後にトークンを更新した日時。毎リクエストの書き込みを避けるため、トークンの更新時だけ書き換える |
| `revoked_at` | timestamptz | null可 | 無効にした日時(ログアウト・同じ端末での再ログイン・使用済みのトークンの再使用・アカウントの停止) |

- インデックス: `user_id`(停止時にまとめて無効にするため)、`(user_id, device_id)`の部分一意インデックス(`revoked_at IS NULL`の行のみ。
  同じユーザー・同じ端末の有効なログイン状態が1つしか無いことをDBで保証する)、`revoked_at`の部分インデックス(パージ用)

`refresh_tokens`(リフレッシュトークン):

| 列 | 型 | 制約 | 内容 |
|---|---|---|---|
| `id` | UUID | 主キー | |
| `auth_session_id` | UUID | NOT NULL、FK(`auth_sessions.id`、ON DELETE CASCADE) | どの端末のログイン状態(トークンの系列)に属するか |
| `token_hash` | CHAR(64) | NOT NULL、一意 | トークンのSHA-256(16進数)。トークンそのものは保存しない |
| `expires_at` | timestamptz | NOT NULL | 発行から30日後 |
| `used_at` | timestamptz | null可 | 更新に使った日時。nullなら未使用(今使っているトークン) |
| `created_at` | timestamptz | NOT NULL | 発行した日時 |

- インデックス: `token_hash`(一意制約。更新時の検索)、`auth_session_id`、`expires_at`(パージ用)
- 1つのログイン状態の中で未使用のトークンは常に1つ。更新は1つのトランザクションで、古いトークンの行を行ロック
  (`SELECT ... FOR UPDATE`)してから`used_at`を入れ、新しいトークンを作る(同時に届いた更新は、後の方が使用済みと判定される)
- 使用済みの行は、再使用の検知のために残す。端末側はsecure storageに最新の1つだけを持つ

その他:
- 既存の`users`の行(テストユーザー`1111...`)は、マイグレーションでは`password_hash`をnullのままにし(ログインできない)、
  シードでパスワードを設定する
- `worker`のパージに追加する: 期限切れ(`expires_at`が過ぎた)のリフレッシュトークンと、無効にしてから30日経った
  ログイン状態(その端末のトークンもCASCADEで消える)を物理削除する
- `auth_sessions`を作らず`refresh_tokens`に系列のIDを持たせる案は、毎回の突き合わせが重くなり、無効にする対象が1行にならないので採らなかった
- アカウントの停止: 管理者が`disabled_at`を入れ、その人の`auth_sessions`を全て無効にする(停止を解除しても前のトークンは使えず、
  ログインし直す)。管理者の画面・APIができるまでは、管理用のコマンド(`python -m app.cli disable-user <email>`・
  `enable-user <email>`)で行う

### 鍵・設定

- ES256の鍵のペア(PEM)は`backend/secrets/`(`.gitignore`済みにする)に置き、`api`にだけ読み取り専用でマウントする。
  生成のコマンドはCLAUDE.mdの「よく使うコマンド」に書く
- 設定: `JWT_PRIVATE_KEY_PATH`・`JWT_PUBLIC_KEY_PATH`、`ACCESS_TOKEN_TTL_MINUTES`(既定15)、`REFRESH_TOKEN_TTL_DAYS`(既定30)
- 追加するパッケージ: `pwdlib[argon2]`、`PyJWT[crypto]`(ES256にcryptographyが必要)

### シード

- 開発用: 管理者1人と、パスワード付き・メールアドレス確認済みのテストユーザー(`1111...`を含む)。argon2のハッシュはSQLでは
  作れないので、管理用のコマンド(`python -m app.cli seed-dev`)で作る。開発用のパスワードは設計メモではなくシードのコード内に置く

### 後で行うこと

- RLS(行レベルのセキュリティ): アプリ層の認証が動いた後に、10/15のバッファか仕上げの枠で追加する。トランザクションごとに
  `SET LOCAL`で今のユーザーを渡し、ポリシーで`user_id`と比べる。管理者・ログイン時の検索・`worker`のパージは例外の条件が要る
- ローカルアカウント(frontend): `frontend/docs/ユーザー機能追加に伴う変更予定.md`の「ローカルアカウント」
- `devices`テーブル: 端末の一覧の画面やFCMの通知(通知用のトークンは端末に属する)を作るときに、`auth_sessions`から端末の情報を分ける。
  `auth_sessions`に`device_id`を記録しているので、後からマイグレーションで移せる
